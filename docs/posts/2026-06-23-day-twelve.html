Tuesday: Hunting for DFT Resources, and a Second Look at Generation Time

Day 11 used fft() as a black box to get a dominant period and a phase argument out of the simulation, with a note left in “What’s Next” to actually learn what the transform is doing rather than keep treating it as a library call. Tuesday went looking for resources to do that properly, rather than diving straight back into mizer.

Where to Actually Learn the DFT

The most useful resources found were:

  • Julius O. Smith III’s Discrete Fourier Transform (DFT), the Stanford CCRMA page on the DFT, which derives the transform itself rather than just stating the formula and lists the standard properties (linearity, the shift and convolution theorems, Parseval’s relation) in one place.
  • YouTube explanations from 3Blue1Brown and Steve Brunton, for the geometric “winding the signal around a circle at different frequencies” intuition that’s harder to get from a written derivation alone.

The rest of Tuesday’s DFT time went into working through that material and starting a proper set of notes rather than anything that produces code or numbers worth showing here.

Limit Cycles

Alongside the DFT, Tuesday’s reading time also went into Strogatz’s Nonlinear Dynamics and Chaos, picking up the limit-cycle chapter that had been queued since Day 11 (the system’s boom-bust oscillation is exactly the kind of self-sustained periodic attractor that chapter is about, and Day 11 had been reasoning about phase and feedback without that theory underneath it).

# Reused from Day 8/11: power spectrum of a (mean-subtracted) signal.
power_spectrum <- function(signal, dt) {
  signal <- signal - mean(signal)
  n      <- length(signal)
  freqs  <- (1:(n - 1)) / (n * dt)
  power  <- Mod(fft(signal))^2
  half   <- seq_len(floor((n - 1) / 2))
  data.frame(freq = freqs[half], period = 1 / freqs[half], power = power[half + 1])
}

Does the Growth Rate Assumption Hold Up?

Day 11 derived a clean prediction for how phase should depend on growth rate, then checked it against the actual data and found it failed: the measured phase curve didn’t fall steadily the way the proof predicted, and the relative phase drop from \(w_{min}\) to \(w_{mat}\) had the wrong sign and was far too small in magnitude. An assumption behind that proof were flagged as suspect: that growth rate is fixed at its steady-state value when the food supply driving it actually oscillates along with everything else. The generation-time number just calculated rests on that same fixed-growth-rate assumption (getEGrowth(params), evaluated at the steady state), so before moving on to the DFT and limit-cycle reading, it was worth checking directly how much that assumption was costing.

Why You Can’t Just Separate Variables for \(g(w,t)\)

The steady-state version of the age calculation rests on separating variables in \(dw/dt = g(w)\):

\[\frac{dw}{g(w)} = dt \quad\Longrightarrow\quad a(w) = \int_{w_{min}}^{w} \frac{dw'}{g(w')}\]

This works because \(g(w)\) depends only on \(w\), so all the \(w\)-stuff can be put on one side and all the \(t\)-stuff on the other before integrating each side independently. The moment growth rate also depends on time, \(g(w,t)\), that move stops being valid:

\[\frac{dw}{g(w,t)} = dt\]

looks the same, but the left side still has a \(t\) buried inside it, and that \(t\) isn’t free to integrate away on its own, because \(w\) and \(t\) are linked along the very trajectory being solved for. Writing \(\int dw/g(w,t)\) in isolation doesn’t mean anything yet: you’d need to already know \(w(t)\) to know what to plug into \(g\) at each step, which is circular.

There’s one case where separation still rescues you: if the time-dependence factors out multiplicatively, \(g(w,t) = g_0(w)\,h(t)\) (e.g. food availability scaling every size class’s growth by the same relative amount), then

\[\frac{dw}{g_0(w)} = h(t)\,dt \quad\Longrightarrow\quad A(w) = H(t) - H(t_{\text{birth}})\]

where \(A(w) = \int_{w_{min}}^w dw'/g_0(w')\) and \(H\) is an antiderivative of \(h\). This still gives a closed form, but a cohort-dependent one: \(t_{\text{peak}}(w) = H^{-1}(A(w) + H(t_{\text{birth}}))\) now depends on \(t_{\text{birth}}\) in a nonlinear way, unlike the steady-state case where every cohort shares the same offset \(a(w)\). There was no good reason to expect mizer’s actual \(g(w,t)\) to factor this cleanly, though, so rather than gamble on that assumption, the honest route is the fully general one: solve \(dw/dt = g(w,t)\) as the coupled equation it is, numerically, for each cohort separately. That’s what project() is already doing internally; the next step just pulls a labelled cohort’s trajectory back out of it after the fact.

Building \(g(w,t)\) From the Simulation’s Own History

getEGrowth() doesn’t have to be evaluated at the steady state. It recomputes growth from whatever population state n and resource state n_pp you hand it, so feeding each saved time step’s actual state back in gives the real, time-varying growth field instead of a single fixed snapshot:

Code 
# Recompute growth at every saved time step in the settled window, using
# that time step's actual (n, n_pp), not the unperturbed steady state.
post     <- times > 300
idx_post <- which(post)
G <- matrix(NA_real_, nrow = length(idx_post), ncol = length(w))
for (k in seq_along(idx_post)) {
  i      <- idx_post[k]
  n_t    <- array(sim_600@n[i, , , drop = FALSE], dim = dim(sim_600@n)[2:3],
                  dimnames = dimnames(sim_600@n)[2:3])
  n_pp_t <- sim_600@n_pp[i, ]
  G[k, ] <- getEGrowth(params, n = n_t, n_pp = n_pp_t)["Anchovy", ]
}
times_post <- times[idx_post]
t_save     <- times_post[2] - times_post[1]   # 0.2, matches the project() calls above

This shows that getEGrowth(params, n = n_t, n_pp = n_pp_t) for a single time step gives a growth profile very close to, but not identical to, the steady-state getEGrowth(params) used above. At \(t=19.8\) (an early, still-settling point), the smallest-size growth rate was 0.00683 vs. 0.00673 from the steady state, a small difference at that particular moment. The whole point of building G across every saved time step is that this difference isn’t constant, it swings with the cycle, and the steady-state calculation used only the time-averaged-looking (but actually unperturbed-equilibrium) snapshot.

Tracking Real Cohorts Through the Oscillation

With G built, a cohort’s trajectory is found by integrating \(dw/dt = g(w,t)\) forward from \(w_{min}\), looking up the growth rate at the cohort’s current size and time at every step rather than assuming a fixed function of size alone:

Code 
# Bilinear-style lookup: blend the two bracketing saved time snapshots, then
# interpolate across size, to get g(w,t) at an arbitrary (t, w).
g_lookup <- function(t, w_now) {
  idx   <- floor((t - times_post[1]) / t_save) + 1
  idx   <- min(max(idx, 1), nrow(G) - 1)
  frac  <- (t - times_post[idx]) / t_save
  g_vec <- (1 - frac) * G[idx, ] + frac * G[idx + 1, ]
  approx(x = w, y = g_vec, xout = w_now, rule = 2)$y
}

# Forward-integrate a single fish born at t_birth through the real,
# time-varying growth field (simple Euler stepping; dt_step is fine enough
# relative to the ~8 year period that finer stepping doesn't change the result).
track_cohort <- function(t_birth, w_min = min(params@w), w_max = max(params@w),
                         dt_step = 0.02) {
  t_now <- t_birth; w_now <- w_min
  t_vec <- t_now;   w_vec <- w_now
  while (w_now < w_max && t_now < max(times_post) - 1) {
    g_now <- g_lookup(t_now, w_now)
    if (is.na(g_now) || g_now <= 0) break
    w_now <- w_now + g_now * dt_step
    t_now <- t_now + dt_step
    t_vec <- c(t_vec, t_now); w_vec <- c(w_vec, w_now)
  }
  data.frame(t = t_vec, w = w_vec, age = t_vec - t_birth)
}

Phase Velocity vs Group Velocity: Why the Two Calculations Disagree

There’s a cleaner way to describe what went wrong with the steady-state estimate and what the cohort-tracking above actually fixed, borrowed from how dispersive waves are normally described.

For a wave built from a single frequency, points of constant phase move through space at the phase velocity, \(v_{\text{phase}} = k/\kappa\), where \(k\) is the (temporal) frequency and \(\kappa\) is the (spatial) wavenumber. A wave packet, a localised pulse built from a narrow spread of frequencies, instead moves at the group velocity, \(v_g = dk/d\kappa\). In a non-dispersive medium these are the same number. In a dispersive one, they aren’t, and the difference is exactly the gap between “where the ripples appear to be” and “where the actual energy is going.”

This system has a direct translation: size \(w\) plays the role of space, real time \(t\) plays the role of time, and Day 11’s \(\kappa(w) = d\varphi/dw = -k/g(w)\) is a wavenumber computed from a single frequency, the dominant FFT peak. That makes the whole Day 11 derivation a phase-velocity calculation: how fast a surface of constant phase, for one Fourier component, moves through size-space. track_cohort() above does something different: it forward-integrates the actual nonlinear \(g(w,t)\) that real fish experience, with no decomposition into frequencies at all. That’s a direct measurement of how fast the real pulse of fish moves through size-space, which is exactly what group velocity means once “wave packet” is replaced with “cohort.”

These two only have to agree if the underlying signal is a clean single sinusoid riding a linear, non-dispersive medium. Neither is true here. Day 8 already found the oscillation is a relaxation-oscillator shape (sharp crash, long plateau) loaded with harmonics, not a pure sine wave, and the growth field \(g(w,t)\) is itself nonlinear, depending on the very population state being transported through it, which is exactly what makes a medium dispersive rather than uniform. The mismatch between Day 11’s phase-velocity calculation and today’s cohort-tracked group velocity isn’t a separate failure from Day 8’s harmonic finding; it’s the same fact, met again in a different calculation.

It also gives a tidier reading of today’s cohort-to-cohort spread. If there were one well-defined phase velocity for this system, every cohort would share exactly the same generation time. Instead the five tracked cohorts came out at 2.46 to 2.81 years, and the period-to-generation-time ratio ranged from 2.97 to 3.38 rather than landing on one fixed number. That spread is the sign of their being dispersion. A single “the” generation time was never quite the right concept for a system like this; there’s a distribution of them, the same way a dispersive pulse doesn’t have one well-defined speed once you look closely enough.

Can You Beat Constant Fishing by Fishing Only the Peaks?

The other Wednesday thread continued an investigation that had been running in parallel this week on the same Anchovy size-spectrum setup: given that biomass oscillates in boom-bust cycles, is it better to fish constantly, or only in pulses timed to the peaks?

An earlier draft of this used a box-selectivity gear catching only “sub-adults” (sizes between half of \(w_{mat}\) and \(w_{mat}\)), i.e. fish that hadn’t yet had a chance to reproduce. That’s not a realistic fishery, so it was replaced with mizer’s built-in knife-edge selectivity at \(w_{mat}\): nothing below maturity weight is ever caught, only mature individuals, the standard “minimum landing size” idealisation.

Separately, the first version of “fish only at the peaks” found peak times once, in advance, by running the unfished trajectory all the way to \(t=600\) and scanning it for local maxima, then baked those fixed times into a constant effort schedule. That’s static, and more importantly it’s circular for any real use of this model: peak timing isn’t knowable in advance without already having run the unfished case to completion first. The fix uses mizer’s setRateFunction() to swap in a custom fishing-mortality function that detects peaks live, from the actual (fished) trajectory as it’s being simulated, with no foreknowledge:

Code 
# Mizer resolves a custom rate function by name via get(), searched from
# wherever mizer's own internal code calls it -- that lookup never reaches a
# closure stashed inside another R function's local frame, so this factory
# (and the name it gets assigned to) has to live at top level, not inside
# modelling_fishing_at_peaks() below.
make_dynamic_peak_FMort <- function(window) {
  state <- new.env()
  state$t_prev     <- NA_real_   # time of the last distinct recorded point
  state$bm_prev1   <- NA_real_   # biomass one recorded step back
  state$bm_prev2   <- NA_real_   # biomass two recorded steps back
  state$fish_until <- -Inf       # fishing stays on until this time

  function(params, n, n_pp, n_other, t, effort, e_growth, pred_mort, ...) {
    bm <- sum(n[1, ] * params@w * params@dw)

    # predictor-corrector calls FMort twice per dt at the same t; only
    # advance the rolling history once per distinct time point
    if (is.na(state$t_prev) || t > state$t_prev) {
      if (!is.na(state$bm_prev2) &&
          state$bm_prev1 > state$bm_prev2 && state$bm_prev1 > bm) {
        # bm_prev1, recorded at state$t_prev, was a local peak in the
        # actual (fished) trajectory -> open/extend the fishing window
        state$fish_until <- max(state$fish_until, state$t_prev + window)
      }
      state$bm_prev2 <- state$bm_prev1
      state$bm_prev1 <- bm
      state$t_prev   <- t
    }

    dynamic_effort <- effort
    dynamic_effort[] <- if (t <= state$fish_until) effort else 0

    mizerFMort(params, n = n, n_pp = n_pp, n_other = n_other, t = t,
               effort = dynamic_effort, e_growth = e_growth, pred_mort = pred_mort, ...)
  }
}

}

make_dynamic_peak_FMort() is a closure factory. The environment it creates (state) is captured by the function it returns, so that function can read and mutate t_prev/bm_prev1/bm_prev2/fish_until across thousands of calls during a single project() run without mizer’s API giving it any explicit mechanism for that. Peak detection itself is the classic “is the middle of three points a local max” test, applied causally: it only confirms bm_prev1 was a peak once a later point (bm) shows biomass has already started falling, so this can only react to a peak one step after it happened, not anticipate one in advance, unlike the old offline version. Once confirmed, a window-year fishing pulse opens from that point forward; overlapping pulses extend rather than reset (max(state$fish_until, ...)). The function never reimplements how selectivity, catchability, and effort combine, it just substitutes a gated effort into mizer’s own mizerFMort(), so only effort changes, never selectivity.

Constant Fishing vs. Fishing the Peaks

Code 
sim_const_fish <- modelling_steady_state(0.001)
sim_peaks      <- modelling_fishing_at_peaks()

plotYield(sim_const_fish, sim_peaks, log = "x", tlim = c(550, 600))

The first version of this comparison used each function’s own default resource scenario (modelling_steady_state()’s default is full resource, modelling_fishing_at_peaks()’s default is heavily depleted resource), which is not a fair comparison of fishing strategies, it’s a comparison of two different ecosystems. Worse, under that mismatch the constant-fishing run produced exactly zero yield from \(t=300\) onward, while total biomass stayed healthy and oscillating. Checking range(selectivity) ruled out a gear bug (it was a proper [0, 1]), which narrowed it to either a real population collapse or a structural mismatch between the two resource scenarios. The code above now matches resource_decrease between the two calls, which should remove that confound, but a clean re-check of the zero-yield anomaly specifically, biomass-above-\(w_{mat}\) over time, with and without fishing, hasn’t been re-run since making that fix. Treat the comparison plot as illustrative of the mechanism, not yet a verified result.

Hunting for the Best Effort and Window

With a working dynamic peaks-only model, the next question was what combination of fishing effort and pulse window maximises yield:

Code 
peak_yield_summary <- function(f_effort, peak_window) {
  sim <- modelling_fishing_at_peaks(f_effort = f_effort, peak_window = peak_window)
  yt  <- getYield(sim)
  t   <- as.numeric(rownames(yt))
  mean(yt[t > 300, ])
}

Best again landed on the boundary: effort = 2, window = 0.5. Widening or narrowing the box just relocates the wall; it never produces an interior maximum.

This shows how raw yield, as an optimisation target, is structurally degenerate here. A pulse removes roughly \(1-e^{-F\cdot\text{window}}\) of the standing mature biomass, a fraction that climbs toward (but can never exceed) 100% as effort rises and the window shrinks. Because the pulse is brief, it never touches the juveniles driving recruitment, so the stock fully rebuilds before the next peak regardless of how hard a given pulse hit it. Nothing in raw yield penalises “more effort, less time”, so the optimum is always at whatever the most extreme effort/shortest window in the search range happens to be: take as much of each peak as possible, as fast as possible, and leave the rest of the cycle alone. That’s a real result about the biology, no biological mechanism here makes brief, intense harvesting unsustainable, but it also means the search needs a different objective before “optimal effort and window” means anything a real fishery could act on.
